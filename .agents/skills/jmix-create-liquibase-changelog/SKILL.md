# Create Liquibase Changelog

Use this skill for every persistent entity or schema change, including adding a
Jmix add-on that owns database tables.

## Steps

1. Find the root changelog path from `application.properties`.
2. Follow the existing naming style: sequential files or date/time folders.
3. Create a new changelog file for the schema change. To add columns to an
   existing table, see "Changing an existing table" below. If the change also
   needs a data fix (a backfill, a reset of a column), first read `references/data-fix.md` in this skill's folder.
4. Make sure the file is reachable from the root `changelog.xml` (see "Root
   changelog reachability").
5. Read the root `changelog.xml` for other included changelogs. A baseline
   changelog creates the whole schema for a fresh database; two signs of one are
   tables older than the current release and changesets with
   `<validCheckSum>ANY</validCheckSum>`. If the project keeps one, first read `references/baseline.md` in this skill's folder.
6. If you add a Jmix add-on that owns persistent entities, first read `references/add-on-changelogs.md` in this skill's folder.
7. Use a changeset id and author that match project style; do not reuse an id
   within the same changelog file.
8. Add `ID` and `VERSION` columns for standard Jmix entities, with the id type
   from "Id column".
9. Add every persistent entity field with exact type, length, precision, scale,
   and nullability.
10. Add foreign keys for references, parent table first (see "Parent → child
    ordering"). If two foreign keys can act on the same row in one statement,
    read **When two referential actions can act on one row** below.
11. Add indexes and unique constraints required by the entity or domain. Every
    index must also be an `@Index` with the same name in the entity's
    `@Table(indexes = ...)`, and the reverse — see **Index parity** in
    `jmix-create-entity`.
12. Verify the table and column names match Java annotations.
13. Use only type macros already present in the project. If no macro exists,
    use the standard Liquibase type.

## Standard types

| Java type | Liquibase type |
| --- | --- |
| UUID | `${uuid.type}` |
| String | `varchar(n)` |
| Integer | `int` |
| Long | `bigint` |
| BigDecimal | `decimal(p,s)` |
| Boolean | `boolean` |
| LocalDate | `date` |
| LocalDateTime | `timestamp` |
| OffsetDateTime / ZonedDateTime | `timestamp with time zone` |
| `@Lob` String (unlimited text) | `clob` |
| `@Lob` byte[] | `blob` |
| FileRef | `varchar(1024)` |
| Enum id string | `varchar(50)` |

A column name must not be a reserved word in any targeted dialect, and the
dialects disagree: PostgreSQL rejects `END` (check with
`select catcode from pg_get_keywords() where word = '<lower-case name>'`), while
HSQLDB accepts SQL-standard keywords as identifiers by default and never warns.
Liquibase writes the name unquoted, so the `createTable` fails only when the
changelog first runs on the production dialect. Rename instead of quoting. See
`jmix-create-entity` (Column names).

## Id column

The id column type comes from the Java id field. Follow how the project's
existing changelogs handle the id.

- `UUID` id: `${uuid.type}`.
- `Long` id generated by `@JmixGeneratedValue`: `bigint` (`int` for an
  `Integer` id). Jmix takes the values from the sequence
  `seq_id_<entity name>`, or from the one named in `sequenceName`, and creates
  that sequence on first use if it does not exist, so the changelog does not
  need to create it. If the project's existing changelogs create their id
  sequences, do the same.
- Assigned natural key: the type of its Java field — `bigint` for a `Long` id,
  not `${uuid.type}`. See `jmix-create-entity` (Id strategy).
- Entity that extends a framework `@MappedSuperclass`: it inherits its key, and
  usually a version and a tenant column with it. No field in the subclass names
  them, but the table must still create them. Read the superclass and take each
  inherited column's name and type from there; these base classes are often
  keyed by an `int`, not `${uuid.type}`.

## Entity table skeleton

```xml
<changeSet id="create-customer" author="app">
    <createTable tableName="CUSTOMER">
        <column name="ID" type="${uuid.type}">
            <constraints nullable="false" primaryKey="true" primaryKeyName="PK_CUSTOMER"/>
        </column>
        <column name="VERSION" type="int">
            <constraints nullable="false"/>
        </column>
        <column name="NAME" type="varchar(100)">
            <constraints nullable="false"/>
        </column>
    </createTable>
</changeSet>
```

## Changing an existing table — `addColumn`, never a second `createTable`

Adding fields to an existing entity (see `jmix-create-entity/references/widening.md`, next to this skill's folder) needs a new changelog file with `addColumn`. Do not edit
the original `createTable` changeset: it is already applied, and changing it
breaks the checksum and fails startup.

```xml
<changeSet id="1" author="app">
    <addColumn tableName="CUSTOMER">
        <column name="NOTES" type="clob"/>
        <column name="LAST_CONTACTED_AT" type="timestamp with time zone"/>
        <column name="MANAGER_ID" type="${uuid.type}"/>
    </addColumn>
</changeSet>

<!-- FK and index for the new reference column: separate changesets -->
<changeSet id="2" author="app">
    <addForeignKeyConstraint baseTableName="CUSTOMER" baseColumnNames="MANAGER_ID"
                             referencedTableName="EMPLOYEE" referencedColumnNames="ID"
                             constraintName="FK_CUSTOMER_ON_MANAGER"/>
    <createIndex indexName="IDX_CUSTOMER_MANAGER" tableName="CUSTOMER">
        <column name="MANAGER_ID"/>
    </createIndex>
</changeSet>
```

- Read the table's original changelog first and match its naming and type style.
- The column type comes from the Java field (see "Standard types").
- A column added to a table that already has rows cannot be `nullable="false"`
  without a default or a data fix: existing rows have no value. Add it nullable,
  add it with a `defaultValue`, or backfill with `<update>` and then tighten (first read
  `references/data-fix.md` in this skill's folder).

## Audit and soft-delete columns

If the entity has audit (`@CreatedBy` / `@CreatedDate` / `@LastModifiedBy` /
`@LastModifiedDate`) or soft-delete (`@DeletedBy` / `@DeletedDate`) annotations,
add the matching columns inside its `<createTable>`. Jmix sets them at runtime,
so keep them nullable (no `nullable="false"`). Add only the columns whose
annotations are on the entity — see `jmix-create-entity` (Auditing and Soft
Delete).

```xml
<column name="CREATED_BY" type="varchar(255)"/>
<column name="CREATED_DATE" type="timestamp"/>
<column name="LAST_MODIFIED_BY" type="varchar(255)"/>
<column name="LAST_MODIFIED_DATE" type="timestamp"/>
<column name="DELETED_BY" type="varchar(255)"/>
<column name="DELETED_DATE" type="timestamp"/>
```

## Parent → child ordering

The parent `createTable` must come before the child's `createTable` /
`addForeignKeyConstraint`. A changeset that references a table not yet created
fails at startup and stops the whole context, including tests that only touch
the data model.

```xml
<!-- parent FIRST -->
<changeSet id="create-parent" author="app">
    <createTable tableName="PARENT">
        <column name="ID" type="${uuid.type}">
            <constraints nullable="false" primaryKey="true" primaryKeyName="PK_PARENT"/>
        </column>
        <column name="VERSION" type="int"><constraints nullable="false"/></column>
        <column name="NAME" type="varchar(100)"><constraints nullable="false"/></column>
    </createTable>
</changeSet>

<!-- child SECOND: its FK references the already-created parent -->
<changeSet id="create-child" author="app">
    <createTable tableName="CHILD">
        <column name="ID" type="${uuid.type}">
            <constraints nullable="false" primaryKey="true" primaryKeyName="PK_CHILD"/>
        </column>
        <column name="VERSION" type="int"><constraints nullable="false"/></column>
        <column name="NAME" type="varchar(100)"><constraints nullable="false"/></column>
        <column name="PARENT_ID" type="${uuid.type}"><constraints nullable="false"/></column>
    </createTable>
    <addForeignKeyConstraint baseTableName="CHILD" baseColumnNames="PARENT_ID"
                             referencedTableName="PARENT" referencedColumnNames="ID"
                             constraintName="FK_CHILD_ON_PARENT"/>
</changeSet>
```

For a composition child, the parent's deletion traits decide which layer removes
the child rows. Check them before choosing `onDelete`:

- Parent has `@DeletedDate` / `@DeletedBy` (soft delete): Jmix enforces the
  cascade at the application layer (`@Composition` +
  `@OnDelete(DeletePolicy.CASCADE)` on the entity). The parent row is never
  physically deleted, so a database `onDelete="CASCADE"` would not fire. Leave
  the FK without `onDelete`.
- Parent has neither (hard delete): the application-layer policy never runs, so
  the database clause is the only thing that removes the children. The child's
  FK must have `onDelete="CASCADE"`.

## Root changelog reachability

Usually the new file goes under the directory covered by the project's
`<includeAll>`:

```xml
<includeAll path="/com/company/app/liquibase/changelog"/>
```

Add an explicit `<include>` only when the project uses explicit includes:

```xml
<include file="/com/company/app/liquibase/changelog/030-customer.xml"/>
```

## Forbidden

- New changelog file that is not reachable from the root changelog.
- An explicit `<include>` for an application changelog in a project that uses `<includeAll>`.
- Reusing a changeset id in the same changelog file.
- Modifying a changeset already applied to a DB: it changes the checksum and Liquibase fails at startup. Add a new changeset instead.
- Raw `UUID` type instead of `${uuid.type}`.
- `${uuid.type}` for a `Long` / `Integer` id or for a key inherited from a framework `@MappedSuperclass` of another type.
- Inherited `@MappedSuperclass` columns (version, tenant and others) missing from the table.
- Creating id sequences in the changelog when the project's existing changelogs do not, or leaving them out when they do.
- Invented type macros such as `${datetime.type}` when the project does not define them.
- Missing `VERSION`.
- Nullable database column for a required Java field.
- Java precision/length different from Liquibase precision/length.
- A table or column name that does not match the Java annotations.
- A column name that is a reserved word in a targeted dialect, or quoting it instead of renaming.
- Missing FK for persistent references.
- A child table / FK changeset ordered before the parent table it references.
- A hard-deleted composition parent whose child FK has no `onDelete="CASCADE"`.
- `onDelete="CASCADE"` on a child FK whose composition parent uses soft delete.
- A second `createTable` for a table that already exists, when the change is new columns (use `addColumn`).
- `nullable="false"` on a column added to a populated table without a default or a backfill.
- `nullable="false"` on audit or soft-delete columns, or such columns for annotations the entity does not have.
- `value=""` where NULL is meant — omit the value attribute instead.
- An index in the changelog with no matching `@Index` in the entity's `@Table`, or the reverse.
- A Jmix add-on with persistent entities whose module changelog is not explicitly reachable from the root changelog.
- A dated migration with no matching entry in the project's baseline changelogs, when the project keeps one.

## Special cases

### When two referential actions can act on one row

Once two foreign keys can act on the same row in one statement, `onDelete` is
not an independent choice per constraint. The common case is a self-referencing
table that also belongs to a cascading owner:

```
EMPLOYEE(DEPARTMENT_ID -> DEPARTMENT ON DELETE CASCADE,
         MANAGER_ID    -> EMPLOYEE   ON DELETE SET NULL)
```

Deleting a department whose head reports to a manager in the same department
makes `FK_EMPLOYEE_ON_DEPARTMENT` delete the row while `FK_EMPLOYEE_ON_MANAGER`
sets its `MANAGER_ID` to null.

Here, use separate statements from the application: clear or delete the
self-references first, then delete the owner.
