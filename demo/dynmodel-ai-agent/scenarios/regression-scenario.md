# Регрессионный сценарий: Dynamic Model AI Agent в браузере

35 ручных проверок агента (шаги 2–36) и редактора динамической модели на одном стенде, для разработчиков и QA:
пересмотр плана до подтверждения, ручные правки рядом с AI, публикация и её отмена, данные в
сгенерированных экранах, расширение модели, отказы, отмена, конфликт двух редакторов, невалидный YAML,
записанная история и сохранность после перезапуска. Автоматические тесты агента живут в репозитории Jmix Premium;
здесь — то, что проверяется только в браузере. Стенды и их запуск описаны в [README](../README_ru.md).

## Шаг 1. Подготовить стенд и запись результатов

Запусти один стенд, например `./stands.sh start lumo-light` (Windows: `.\stands.ps1 start lumo-light`),
открой `http://localhost:8093/b2b-crm/`, войди как `admin` / `admin` и выбери русский язык.
Весь прогон идёт на одном стенде. Настройки агента для стендов уже заданы в `application.properties`
и скриптах запуска: ручное подтверждение плана, до 24 шагов в плане, четыре минуты на ход.
Останавливай стенд только командой `stop`: после принудительного завершения его база не восстановится.
В отчёте укажи стенд и commit ID этой ветки, Jmix и Jmix Premium, из которых собран jar.

Открой настройки динамической модели в одной вкладке браузера, а в другой — Инспектор сущностей:
`http://localhost:8093/b2b-crm/datatl/entity-inspector`. Экрана истории агента в этой версии нет;
записанную историю видно в сущностях `dmagent_*` Инспектора (шаг 35).
«Визуальный», «Код» и «AI» ниже — режимы одного редактора (переключатель в заголовке экрана).
Не открывай тот же разговор во второй вкладке браузера в режиме AI.

Проверь отсутствие сущностей `QaClient`, `QaDeal`, `QaReason`, `QaParticipant`, `QaProbe`,
`QaScratch`, `QaCancelled`. Если имена заняты, до начала замени префикс `Qa` во всех запросах
этого прогона, например на `QaRun2`. Старые сущности не удаляй ради повторного запуска.

Для каждого шага записывай PASS / FAIL / BLOCKED / NOT RUN, фактический результат и ссылку
на скриншот или лог. Для AI-запросов добавляй время и текст запроса, а conversation ID и run ID
бери в Инспекторе сущностей (шаг 35).
Перед первой публикацией сохрани исходную ревизию и YAML в артефакты прогона.
Если результат шага неверен, зафиксируй его до ручного исправления; зависимые шаги отмечай BLOCKED.
Не подтверждай план, затрагивающий посторонние сущности.

## Шаг 2. Запросить клиентов и сделки

В AI начни новый разговор и отправь:

```text
Создай отдельные тестовые сущности QaClient «QA-клиенты» и QaDeal «QA-сделки».
QaClient: companyName STRING «Название компании», обязательное, название записи;
phone STRING «Телефон», необязательное, длина 30.
QaDeal: name STRING «Название», обязательное, название записи;
client — обязательная одиночная ссылка на QaClient;
amount DECIMAL «Сумма», необязательное;
rejectionReason TEXT «Причина отказа», необязательное.
Обоим нужны список, карточка и пункт меню в существующем разделе catalog.
Существующие сущности CRM не меняй. Подготовь план, публикацию выполню сам.
```

Пока не подтверждай. В плане должны быть две сущности, шесть полей вместе со ссылкой,
экраны и два пункта меню. В строках плана проверь типы, длину телефона («до 30 символов»),
обязательность и «название записи» у двух названий. Технические имена `QaClient`, `companyName` и
остальные видны в подсказке при наведении на сущность или поле, вместе с подписями на всех языках.
Количество операций может отличаться при отдельном создании списка и карточки; лишних изменений быть не должно.

Переключись в режимы «Визуальный» и «Код»: новые сущности ещё отсутствуют, редактирование и кнопка
«Применить» заблокированы. Вернись в AI: тот же план по-прежнему ожидает подтверждения.

## Шаг 3. Изменить неподтверждённый план

В том же разговоре отправь:

```text
Дополни предыдущий план, сохранив все его изменения.
QaClient добавь notes TEXT «Заметки о клиенте».
QaDeal добавь nextContactDate DATE «Дата следующего контакта» и urgent BOOLEAN «Срочно».
Все три поля необязательные. nextContactDate поставь перед amount.
```

Новый план содержит обе сущности и все девять полей вместе со ссылкой.
Телефон остаётся длиной 30. Дата предшествует сумме; взаимный порядок остальных полей пока не задан.
Подтвердить можно только текущий план. Открой старое вложение в AI: это снимок только для чтения,
кнопки подтверждения у него нет.
Старый снимок не содержит notes, nextContactDate и urgent; новый содержит их.

## Шаг 4. Подтвердить план и сверить черновик

Нажми «Подтвердить план» один раз. Во время выполнения в чате обновляются строки активности.
После завершения открой вложение результата и перейди в режим «Визуальный».

| Сущность | Поле | Что должно быть |
| --- | --- | --- |
| QaClient | companyName | STRING, обязательное, название записи |
| QaClient | phone | STRING, длина 30, необязательное |
| QaClient | notes | TEXT, необязательное |
| QaDeal | name | STRING, обязательное, название записи |
| QaDeal | client | Одиночная обязательная ссылка на QaClient |
| QaDeal | nextContactDate | DATE, необязательное, перед amount |
| QaDeal | amount | DECIMAL, необязательное |
| QaDeal | urgent | BOOLEAN, необязательное |
| QaDeal | rejectionReason | TEXT, необязательное |

У обоих есть список, карточка и меню в `catalog`. В режиме «Код» — те же определения.
Редактор снова доступен для правок, но изменения ещё не опубликованы: в основном меню приложения
новых списков пока нет. «Применить» не нажимай.

Вложение «Подготовленные изменения» совпадает с редактором: сущности, поля, типы, признаки,
порядок, экраны и меню. Снимок плана содержит намерения, снимок результата — полученную конфигурацию.
Старый план из шага 2 остаётся прежним.

## Шаг 5. Сверить шаги выполнения

Под ответом с планом из шага 3 нажми ссылку «Шагов: N»: в боковой панели этапы планирования
«Читаю текущую модель», «Разбираю запрос», «Готовлю план», «Проверяю план», каждый со статусом
и длительностью. Ожидание подтверждения не выглядит ошибкой.

Затем нажми ту же ссылку под ответом с результатом шага 4: строки операций и последней
«Проверяю подготовленные изменения». Сопоставь строки операций с утверждённым планом: на каждую
операцию плана одна строка («Создать сущность», «Добавить атрибут», «Добавить ссылку», «Создать экраны»,
«Добавить пункт меню»). Обе строки «Создать сущность» идут раньше «Добавить ссылку». Нет операций
из отменённого плана, повторных созданий или публикации агентом.

После завершения ни у одной строки не остаётся индикатора выполнения. Строки показывают только
названия шагов: аргументов операций и результатов справочных инструментов в интерфейсе нет.

Если модель сама исправляла предложение, в списке есть строка «Исправляю план · попытка · N / M».
Её отсутствие в успешном запросе нормально; эту ветку принудительно проверяют автоматические тесты Jmix Premium.
Справочные шаги вроде «Читаю структуру сущности» есть только там, где агент их вызывал;
проверка не требует вызова каждого справочного инструмента в одном запросе.

## Шаг 6. Добавить поле через визуальный редактор

В режиме «Визуальный» добавь `QaClient.city`: STRING, необязательное, не название записи,
русская подпись «Город», английская `City`. Поставь после notes.
Перейди в режим «Код»: поле присутствует ровно один раз, остальное определение не изменилось.
Вернись в AI и открой результат шага 4: это последний перенесённый результат, поэтому карточка
показывает модель редактора как есть, вместе с city.

## Шаг 7. Изменить подпись через код

В режиме «Код» найди существующую русскую подпись `QaClient.city` и замени только её на
«Город доставки». Не меняй структуру YAML, техническое имя или английское `City`.
Переключись в режим «Визуальный»: у клиента четыре поля, city стоит после notes,
русская подпись новая, английская прежняя.

Сними YAML текущего редактора для сравнения со следующим шагом.

## Шаг 8. Спросить агента о ручных изменениях

```text
Ничего не меняй. Перечисли текущие поля QaClient в порядке отображения,
с техническими именами и русскими подписями. Есть ли city, какая у него подпись?
Эти изменения уже опубликованы или пока находятся в редакторе?
```

Ожидаются companyName, phone, notes, city; последняя подпись «Город доставки».
Агент говорит о неопубликованных изменениях. Ответ не создаёт план, новое вложение черновика
и строки операций, YAML не меняется.

Если агент отрицает city или неверно описывает порядок, зафиксируй FAIL независимо от того,
что поле видно в редакторе.

## Шаг 9. Продолжить через AI после ручных правок

```text
В текущем редакторе QaClient переименуй только русскую подпись notes
в «Комментарий менеджера». Сохрани city, его подписи и порядок всех полей.
Остальные сущности и поля не меняй.
```

План меняет подпись существующего notes, без удаления и пересоздания поля.
Подтверди. В режимах «Визуальный» и «Код» сохранились city / «Город доставки» / `City`,
длина телефона 30 и все поля сделки. Старые планы не исполнились повторно.
Новое вложение результата содержит city и новую подпись notes. Результат может показывать
только затронутую сущность;
сохранность остальных проверяй в полном редакторе.

## Шаг 10. Отменить публикацию в диалоге подтверждения

Нажми «Применить». Пока открыт диалог со списком изменений,
попытка начать новый AI-запрос не должна запустить Run.
В списке изменений есть создание клиентов и сделок, включая ручное city.
Закрой диалог, не нажимая «Применить изменения». YAML остаётся в редакторе, ревизия не изменилась,
меню новых сущностей не появилось, в чате нет сообщения об успешной публикации.

## Шаг 11. Опубликовать клиентов и сделки

Снова нажми «Применить» и в диалоге — «Применить изменения». Дождись успеха, запиши новую ревизию.
Открой вложение «Применённые изменения»: оно описывает опубликованный результат,
включая city и новую подпись notes. Закрытие и повторное открытие не создаёт второго сообщения о публикации.
Черновик предыдущего Run и публикация остаются отдельными вложениями.

Закрой настройки. В `catalog` доступны «QA-клиенты» и «QA-сделки».
Повторно открой настройки: опубликованные определения сохранились.

## Шаг 12. Создать и перечитать бизнес-данные

Создай клиента «Север»: телефон `+79000000001`, город «Казань», комментарий «Оптовые поставки».
Создай «Маяк» с пустыми необязательными полями.
Попробуй сохранить ещё одного клиента без названия: сохранение блокируется на обязательном поле.
Отмени эту карточку.

Создай сделку «Первая поставка»: клиент «Север», дата следующего контакта `24.09.2026`,
сумма `12500,50`, «Срочно» включено, текст причины отказа «Не согласовали бюджет».
Дата отображается перед суммой. Без названия или клиента сделка не сохраняется.
Сохрани корректную запись, закрой и открой её: все значения сохранились,
ссылка показывает «Север», а не UUID. Ошибки сгенерированных экранов записывай отдельно
от ошибок агента с указанием фактического слоя сбоя.

## Шаг 13. Запросить справочник и участников

Открой настройки → AI, начни новый разговор:

```text
Расширь наши QaClient и QaDeal, сохранив существующие поля, экраны и данные.
Создай QaReason «QA-причины отказа»: name STRING «Название», обязательное,
название записи; список, карточка и меню в catalog.
В QaDeal добавь reason — необязательную одиночную ссылку «Причина из справочника»
на QaReason. Старое текстовое rejectionReason оставь.
Создай QaParticipant «QA-участники сделки»: client — обязательная одиночная ссылка
на QaClient, role STRING «Роль» — необязательное название записи.
Участнику нужна только карточка, без списка и отдельного меню.
QaDeal добавь participants — коллекцию QaParticipant «Участники».
Пункт меню QaDeal поставь перед существующим пунктом QaClient внутри catalog.
```

| Изменение | Что проверить в плане |
| --- | --- |
| QaReason | Новая сущность; name «Текст», обязательный, название записи |
| Экраны QaReason | «Список и карточка»; меню в существующем catalog |
| QaDeal.reason | «Добавить» ссылку «→ QA-причины отказа», без «обязательный» и «несколько значений» |
| QaDeal.rejectionReason | Старый длинный текст сохраняется, имя не используется для новой ссылки |
| QaParticipant | Новая сущность; client «→ QA-клиенты», обязательный, без «несколько значений» |
| QaParticipant.role | «Текст», название записи, без «обязательный» |
| Экраны QaParticipant | Только «Карточка», без списка и меню |
| QaDeal.participants | «→ QA-участники сделки», «несколько значений», без «обязательный» |
| Меню QaDeal | «Переместить» существующий пункт в catalog «перед» пунктом QaClient |

Прямой обязательный `QaDeal.client` остаётся. Технические имена проверяй в подсказках при наведении.
Не требуй фиксированного числа операций при одинаковом конечном результате.

## Шаг 14. Проверить второй черновик и опубликовать

Подтверди план. В редакторе четыре бизнес-сущности. Сверь таблицу шага 13,
старые поля шага 4, city и подпись notes. У участника нет списка и пункта меню.
Меню сделки перемещено, а не продублировано. В режиме «Код» проверь технические имена целей ссылок.

Сверь шаги выполнения с планом по шагу 5: каждая новая сущность создаётся раньше ссылки на неё.
Нажми «Применить», подтверди и открой новое вложение «Применённые изменения».

## Шаг 15. Проверить данные после расширения

Создай в справочнике причину «Не согласовали бюджет».
Открой «Первая поставка»: старый текст rejectionReason остался, новая reason пока пустая.
Выбери созданную причину. Добавь участника с клиентом «Маяк» и ролью «Партнёр».
Добавь второго с клиентом «Север» и ролью «Заказчик». Без клиента участник не сохраняется.
Сохрани сделку, открой снова: обе строки коллекции и одиночные ссылки сохранены.
Удали только строку участника «Партнёр», сохрани и перечитай: в сделке остался один участник,
клиент «Маяк» существует. У клиента «Север» сохранились город и комментарий.

В меню сделка перед клиентами, справочник доступен, самостоятельного списка участников нет.
Изменения бизнес-записей не порождают в чате агента новых планов или сообщений о публикации.

## Шаг 16. Сравнить просмотрщики и поведение вложений

Открой в AI текущего разговора по очереди план, результат и публикацию.

Сравни при ширине окна 1600, 1280 и 900 px, затем в светлой и тёмной теме:
заголовок и бейдж только для чтения, расположение крестика, отступы заголовка и тела,
рамку карточки, подпись «Атрибуты в порядке отображения», строки полей, секции экранов и меню.
Длинный заголовок переносится, не закрывает бейдж и крестик. Панель помещается в окне;
длинный результат прокручивается до последнего поля, без обрезанного текста.

Закрой панель, открой другой тип вложения, затем вложение другого Run этого разговора.
Нет оставшихся строк, действий или заголовка предыдущего снимка. После закрытия
основное содержимое снова доступно. Повторное открытие вложения не запускает агента,
не меняет YAML и ревизию. В панели снимка нет кнопок «Подтвердить план» и «Отменить выполнение».
Для результата с одной сущностью и с несколькими проверь соответствующие варианты карточки;
отсутствие лишнего уровня раскрытия у одной сущности нормально.

## Шаг 17. Проверить Markdown и ответы без изменений

В AI текущего редактора отправь:

```text
Ничего не меняй. Объясни связь QaDeal с QaClient и QaParticipant.
Ответь в Markdown: короткий заголовок, список, таблица «Поле | Цель | Кратность»
и блок кода с техническими именами этих двух ссылок. Название QaDeal выдели жирным.
```

Сверь ответ в AI: заголовок, список, таблица, жирный текст и блок кода
отрисованы, маркеры Markdown не выведены сплошным текстом. Горизонтальная прокрутка
длинного кода не раздвигает весь экран. Если модель пропустила формат, один раз попроси
переформатировать тот же ответ; проверку отсутствующего элемента не отмечай PASS.
Сообщение пользователя может оставаться обычным текстом. Новый план и черновик не появились.
